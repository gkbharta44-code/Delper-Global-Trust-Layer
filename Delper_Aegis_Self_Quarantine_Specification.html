Delper Aegis: Self-Quarantine Software Specification

Companion to the Delper Aegis Exhaustive Executive Summary (revised October 2026). Maps each threat in the Splunk "Top 50 Cybersecurity Threats" contents to the software that detects it and contains it.

1. Scope and Design Rule

This specification adds a self-quarantine capability to Aegis. A threat is detected, classified, contained, verified, and then released or escalated, with every step recorded in the sealed quarantine store. Containment is always a network, identity, or cloud action, or a safe-state action on the host. No containment step writes to a PLC or changes a control program, which preserves the hardware write-lock described in Section 2 of the summary.

Safety rule for OT: any action that could change a physical process (isolating a controller, stopping a workload, cutting a link to a running line) runs only in a last-known-safe state and requires a human approval record, unless the safe-state rule in Section 3 applies.
Hardware boundary: the Delper Guard device can enforce only what crosses the plant network. Phishing, identity, SaaS, and cloud threats need connectors to the customer's identity provider, email and web gateways, endpoint tools, and cloud accounts. These connectors are software, and they are listed as required modules below. The summary does not currently price or scope them.

3. Quarantine State Machine

  1. Detect: QG-TI or QG-DPI raises a signal with a threat ID from the table in Section 4.
  2. Classify: QG-ORCH selects the playbook and confidence level. Low confidence records the event and does not contain.
  3. Contain: the playbook's actions run, scoped to the smallest affected unit (flow, session, host, account, workload, or segment). Safe-state rule: if an OT action could affect a running process, the Guard holds the last-known-safe state and waits for approval.
  4. Preserve: QG-SEAL records the evidence before any destructive step, including memory capture and configuration snapshots.
  5. Verify: QG-TI confirms the containment held, and QG-PV checks integrity of the affected component.
  6. Release or escalate: release on the playbook's condition, or hand off to a named human responder. Every transition is written to QG-SEAL.

Default timers: containment reviewed within one hour, release decisions within 24 hours, and a forced human review at 7 days for any quarantine still open. Automatic release never applies to insider, process-affecting, or legal-hold cases.

5. Build Order

  1. QG-SEAL and QG-ORCH, so every later action is recorded and gated.
  2. QG-NET and QG-DPI quarantine paths, covering OT and network threats (rows 2, 5, 11, 27–29, 31–32).
  3. QG-IDP, QG-EDR, and QG-MWG connectors, covering identity, endpoint, and email threats (rows 3, 17, 20–26, 30, 33–35, 41–47).
  4. QG-CLD and QG-AIG, covering cloud and AI threats (rows 6–16, 48, 52).
  5. QG-MIG and QG-PV, covering supply chain and patch integrity (rows 10, 40, and virtual patches used across the table).
Not yet validated: detection thresholds, timers, and playbook release conditions are proposals. They need testing in shadow mode before any live enforcement, consistent with the 60-day shadow-mode recommendation in Section 10 of the summary.
